 City Brain Convergence — Scenario Orchestration Report

## Shared scenario pipeline

All five existing scenarios now run through the same `LiveCity` scenario
coordinator, Twin sensor sampling path, TwinFacade, and observability sinks.
Scenario events carry `event_id`, `correlation_id`, `scenario_id`, timestamp,
event type, source, payload, and a device ID when applicable. Observed sensor
event IDs are attached to the related Brain decision and final command outcome.

The coordinator uses the existing scenario JSON data and does not fabricate
Brain decisions or Guardian verdicts. Brain commands and Guardian
isolation/restoration are recognized only when authenticated callers use the
existing inbound interfaces. Guardian semantics are veto-only because the
current contract does not expose a request-bound positive approval result.
Pending events are not represented as partner responses.

An accepted actuator command continues through the existing TwinFacade
permissions, idempotency, quarantine, and safety checks. Its successful result
is logged as executed only after `LiveCity` commits the corresponding CityCore
effect. Duplicate requests use the existing request ID idempotency behavior.
No existing MCP tool or partner REST contract was changed.

## Scenario outcomes and limitations

| ID | Existing scenario | Shared Twin behavior | Partner / effect behavior |
|---|---|---|---|
| T5 / SCN-01 | Port sensor spoof: actual input 40 cm, false report 180 cm. | Runs through SensorBank and detects the actual/reported mismatch in private state. Unsafe commands linked to the sensor are blocked unless a valid configured backup reading is supplied. | Guardian remains pending until it actually isolates the sensor; Brain remains pending until it actually responds. No automatic flood action is claimed. |
| SCN-02 | Port level seeded to 110 cm. | A forced reading is sampled and published through the normal Twin reading pipeline. | Real Brain commands can pass through TwinFacade and commit to CityCore. No command is generated by the scenario runner. |
| SCN-03 | Frozen traffic and dead industrial temperature feed with registered backup. | Injects only scenario-declared faults and seed values; the frozen traffic's actual value changes while its STUCK report remains at its last valid sample. The dead reading is unavailable. | A command associated with the temperature sensor requires an existing backup ID, valid non-null reading matching its actual input, and a link to the same target. Guardian and Brain actions are not synthesized. |
| SCN-04 | Guardian containment of PRT-PMP-01; scenario lists PRT-PMP-02 as backup. | Waits for real Guardian isolation and retains the standard Twin quarantine gate. | The current device catalog maps both pump IDs to the same physical CityCore target. Therefore the named backup is not an eligible independent fallback after that target is quarantined; no unsafe bypass or substitute device is invented. |
| SCN-05 | Seeded Downtown traffic value and scenario-local Residential air feed. | Traffic uses the registered Twin sensor. `RES-AIR-TEST-01` is emitted only as a labeled fixture event and is never added to the sensor registry. | Only real Brain commands to existing eligible actuators can affect CityCore. No fixture-based Guardian or Brain response is claimed. |

Partner services are not launched by this repository. A run can remain pending
until the Brain or Guardian teams call the Twin's existing authenticated
interfaces. The local dashboard scenario selector and `POST
/api/operator/scenario` route are operator-session authenticated and do not
change the partner contracts.

python scenarios/run.py --scenario scn-03

starting `python tools/run_twin.py`. The dashboard and MCP share one LiveCity
owner. For each run, verify the lifecycle correlation ID, sensor reading,
partner action (only if an external authenticated caller sent one), and

execution.

## Integration campaign — 2026-11-02

The campaign ran each scenario in a fresh `LiveCity`, ran the five scenarios
sequentially with supported resets, and exercised controlled overlapping,
duplicate, stale, competing, and failed command cases. All five isolated
scenario paths, the sequential reset path, and the controlled cross-scenario
cases passed. Scenario evidence includes operator frames, event-store exports,
ordered Twin events, and nine sanitized JSONL audit logs.

| Scenario | Result | CityCore revision before → after command | Verified actuator outcome |
|---|---|---:|---|
| SCN-01 / T5 | PASS | 70 → 70 | Spoof-linked pump command rejected; no additional effect. |
| SCN-02 | PASS | 8 → 9 | Pump speed changed from 0.0 to 0.3; duplicate request replayed without another revision. |
| SCN-03 | PASS | 10 → 11 | No-backup command rejected; validated backup-feed command changed valve opening from 0.3333 to 0.25. |
| SCN-04 | PASS | 7 → 7 | Guardian test call isolated primary; primary and same-target alias commands rejected. Sensor update is not defined by this scenario. |
| SCN-05 | PASS | 12 → 13 | Downtown signal changed from normal to priority; air feed remained fixture-only. |

Actual Brain and Guardian services were **BLOCKED / NOT TESTED**: this
repository has no partner service clients or running partner processes.
Campaign role calls exercised the real TwinFacade boundary but are not claimed
as service responses. A true process crash was not executed. Kafka interruption
was not tested because no Kafka runtime is integrated.

The recovery probe exposed a **FAIL**: after recreating the in-memory owner, the
same request ID was accepted again and produced a new CityCore effect. State and
idempotency records are in-memory only; durable restart restoration and
cross-process duplicate prevention remain unimplemented.

## SCN-06 — controlled communication failure and recovery

SCN-06 adds deterministic, scenario-local availability injection for the
Brain-facing and Guardian-facing inbound Twin interfaces. It records normal,
unavailable, and recovered states; blocks Brain commands while the Brain
channel is down; blocks Guardian isolate/restore and operator restoration while
Guardian is down; and fails actuator authorization closed while Guardian
remains unavailable.
These are local injected states, not real network disconnections or partner
service probes. The repository has no production Brain/Guardian clients and no
pending-command queue, so rejected outage work is not automatically replayed.
A delayed request after recovery goes through the normal state-revision,
authorization, quarantine, and idempotency checks again.

The dedicated campaign passed its deterministic checks, including preservation
of an existing quarantine, stale-revision rejection, one CityCore effect after
recovery, safe duplicate replay, changed-payload idempotency conflict, event
correlation, dashboard-frame capture, and sanitized audit evidence. Targeted
orchestration and dashboard tests also passed. This does not resolve the
separate durability defect found by the previous owner-recreation campaign.
See the [Scenario Book](./docs/SCENARIO_BOOK.md) and
[`campaign.json`](./test-evidence/scn06-20261102T162055.402283Z-2fe9bc5c/campaign.json).
